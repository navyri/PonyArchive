1. Nombre del proyecto e integrantes

Proyecto: PonyArchive — biblioteca inteligente de la serie My Little Pony: Friendship Is Magic con una función especial, el Friendship Journal (consulta temática y comparación de episodios y personajes).

Integrante: Mariana Lemus Esguerra (trabajo individual, conforme a DEC-01).

El sistema responde preguntas sobre la serie usando exclusivamente documentos indexados (episodios, personajes, fichas narrativas propias, notas de contexto del curso y archivos subidos por cada usuario). Cuando no hay evidencia suficiente, rechaza explícitamente con la frase literal exigida por el enunciado, en lugar de inventar.

2. Tema seleccionado y descripción del problema

Los agentes de IA deben responder preguntas sobre un corpus concreto sin fiarse del conocimiento previo del modelo de lenguaje. El problema práctico es doble:

  1. Respuestas fundamentadas: una pregunta como «¿qué le ocurre a Twilight Sparkle en Lesson Zero?» debe responderse con información recuperada de los documentos y citando la fuente, no con la memoria paramétrica del LLM, que puede ser imprecisa o estar desactualizada.
  2. Rechazo honesto: ante preguntas fuera del corpus (p. ej. recetas de cocina o fórmulas de química), el sistema debe decir literalmente «No tengo suficiente información en mi base de conocimiento para responder esa pregunta.» en lugar de generar una respuesta plausiblemente falsa.

El dominio elegido — Friendship Is Magic — aporta un corpus amplio y verificable (243 episodios y 555 personajes descargados de la Pony API pública) y permite, además, un caso real de conocimiento de contexto: datos que el equipo conoce por la asignatura pero que no están en ningún documento público (ver §7, notas de contexto del curso).

Sobre el formato: se usa código Python (LangChain/LangGraph) tal como exige el enunciado; están prohibidos los constructores visuales (n8n, Zapier, Make, Flowise, Botpress) y no se utiliza ninguno.

3. Arquitectura general y diagrama de arquitectura

El sistema son tres piezas desacopladas más un servicio externo opcional:

  • Backend (FastAPI + LangGraph): API REST con 21 endpoints, autenticación JWT, pipeline de ingesta y el grafo del agente.
  • Frontend (React + Vite + TypeScript): interfaz con chat, documentos, historial y Friendship Journal; habla exclusivamente con el backend mediante /api.
  • Persistencia: SQLite (usuarios, documentos, conversaciones, mensajes) y ChromaDB (fragmentos + vectores) en disco.
  • Modelo local: Ollama corriendo en el portátil del equipo; el backend lo consumió por HTTP (OLLAMA_BASE_URL).

Flujo de una consulta

Usuario (React) --POST /api/chat--> FastAPI --grafo LangGraph-->
   validate_intent --> retrieve (ChromaDB) --> evaluate_sufficiency
        |                  |                        |
        |                  +--> evidencia suficiente --> generate --> validate_answer --> persist
        |                  +--> sin evidencia ------------------------------^ (rechazo literal)
        +--> consulta de catálogo (conteos por SQL) --> persist
FastAPI --HTTP--> Ollama (qwen3.5:4b, local)   |   Respuesta + fuentes --> React

Persistencia y aislamiento

Cada documento pertenece a un usuario (Document.user_id). Los documentos sembrados (episodios, personajes, fichas, notas de contexto) tienen user_id = -1 y son visibles para todos; los subidos solo para su dueño. Todos los listados y las búsquedas aplican ese filtro (cláusula $or [user_id = -1, user_id = usuario]), lo que fue verificado con los casos T10/T10b del smoke test (dos usuarios con cargas cruzadas).

7. Descripción del agente y del flujo de LangGraph

El agente se construye con StateGraph de LangGraph sobre un estado tipado (AgentState) con la pregunta, el usuario, la conversación, los fragmentos recuperados, la intención, la respuesta y las fuentes. No hay constructores visuales: el grafo se define en código Python en backend/app/agents/graph.py.

Nodos

NodoFunción
validate_intentClasifica la intención con el LLM (dominio, catalogo, fuera_de_dominio) y propone filtros (tipo de documento, título, tema) con valores por defecto seguros
retrieveBúsqueda vectorial en Chroma con filtro de visibilidad; prioriza los documentos subidos por el usuario (+0,05 de bonificación) y hace una búsqueda general complementaria siempre que haya filtros
evaluate_sufficiencyDecide si hay evidencia: umbral de similitud y reglas por tipo de documento; si no la hay, marca refused con la frase literal
catalog_queryPara consultas de conteo/católogo, responde con SQL sobre SQLite (E7) sin pasar por el LLM
generatePrompt restringido: responder solo con el contexto recuperado, citando fuentes con [n]
validate_answerComprueba la respuesta generada (entidades citadas presentes en el contexto, presencia de fuentes); si falla, deriva a reject
rejectEmite el mensaje de rechazo literal exigido
persistGuarda pregunta y respuesta en la conversación del usuario

Aristas y rutas condicionales

START --> validate_intent
validate_intent --(condicional)--> catalog_query | retrieve
retrieve --> evaluate_sufficiency
evaluate_sufficiency --(condicional)--> generate | reject
generate --> validate_answer
validate_answer --(condicional)--> persist | reject   (rechazo si la validación falla)
catalog_query --> persist ; reject --> persist ; persist --> END
Nota sobre el conocimiento de contexto (DEC-14): la intención fuera_de_dominio recupera antes de decidir. Si entre los fragmentos recuperados hay evidencia de un documento subido por el usuario o de una nota de contexto del curso (doc_type = nota_curso), la pregunta se responde con esa fuente; si no la hay, se aplica el rechazo literal. Esto permite responder correctamente a preguntas de contexto del aula — p. ej. «¿A Duvan Gomez le pega la esposa?» → «Según la nota de contexto del curso, a Duvan Gomez le pega la esposa y lo deja morado» (fuente citada, similitud 0,904) — sin introducir conocimiento inventado.

8. Modelo local utilizado y base de datos vectorial

Modelo de lenguaje

  • Modelo: qwen3.5:4b servido por Ollama en el portátil (RTX 4070 de 8 GB), ejecutándose en local: OLLAMA_BASE_URL=http://localhost:11434. No depende de ningún modelo comercial (requisito T3/R-2).
  • Configuración: reasoning=False (las primeras pruebas devolvían solo razonamiento vacío), num_ctx=8192, temperatura baja en RAG. Respaldo: qwen2.5:3b.
  • Rendimiento: 67 tok/s; primera carga ≈45 s y 3–18 s por respuesta después.
  • Justificación (§8 del enunciado): se eligió un modelo de 4B por tres razones: (1) cabe en 8 GB de VRAM junto a los embeddings sin descargar a CPU; (2) razona bien en español para tareas de síntesis sobre contexto; (3) es local y gratuito, requisito del trabajo. Un 7B tendría mejor calidad nominal pero empeoraría la latencia de la demostración.

Embeddings y base vectorial

  • Modelo de embeddings: intfloat/multilingual-e5-small (384 dimensiones) con sentence-transformers, aplicando los prefijos query: y passage: que e5 exige. Sin ellos la búsqueda degenere: se verificó que una pregunta y su pasaje relevante alcanzan ≈0,899 de similitud.
  • Base vectorial: ChromaDB persistente en backend/vectorstore. Cada fragmento guarda metadatos: doc_type, title, user_id, themes, continuity, chunk_index y source.
  • Parámetros: TOP_K=6 fragmentos por consulta y SIMILARITY_THRESHOLD=0.62 (calibrado con preguntas de prueba). La distancia de Chroma se convierte a similitud (1 - distancia).
  • Escala actual: 816 documentos → 819 fragmentos en local (814 en el contenedor Docker tras importar la Pony API + semillas).

9. Proceso de carga de documentos

Hay tres vías de entrada, todas con el mismo pipeline final:

  1. Importación del catálogo (POST /api/import/episodes|characters o scripts/import_pony.py): descarga de la Pony API con reintentos y paginación, normaliza campos y genera un texto por registro.
  2. Semillas en el arranque (seed.py): 10 fichas narrativas propias (DEC-10, redacción propia porque la API no tiene campos narrativos) y las notas de contexto del curso (DEC-14). Idempotentes: no duplican si ya existen.
  3. Carga por el usuario (POST /api/documents): archivos .txt y .md.

Pipeline

texto --> troceado (fragmentos con solapamiento)
      --> deduplicación por content_hash (y por usuario, para no descartar cargas ajenas)
      --> embed_passages("passage: ...") con e5-small
      --> ChromaDB.add(fragmento + metadatos)   +   fila en SQLite (doc original)

La relación fragmento → documento original queda en el metadato doc_id, de modo que cada fuente devuelta por una consulta puede reconstruirse hasta el documento (requisito T4). Una segunda ejecución de la importación omite los 798 duplicados: la ingesta es idempotente.

10. Estrategias implementadas para evitar alucinaciones

El enunciado exige al menos 2; se implementaron 7 (E1–E7):

IDEstrategiaDescripción y ubicación
E1Umbral de similitudSolo se aceptan fragmentos con similitud ≥ 0,62 (SIMILARITY_THRESHOLD); los descartados se registran en las notas de recuperación
E2Nodo de suficienciaevaluate_sufficiency: antes de generar, decide con reglas explícitas si hay evidencia; sin ella, no se invoca al LLM y se rechaza
E3Prompt restringidogenerate ordena responder solo con el contexto recuperado, citar con [n] y no completar con conocimiento previo
E4Rechazo literalMensaje fijo exacto: «No tengo suficiente información en mi base de conocimiento para responder esa pregunta.» (casos T04/T05)
E5Fuentes obligatoriasLa respuesta viaja con su lista de fuentes (título, tipo, similitud); la UI las muestra y un giro sin fuentes se considera inválido
E6Verificación de entidadesvalidate_answer comprueba que las entidades/cifras citadas aparecen en el contexto; si no, deriva al rechazo
E7Conteos por SQLLas preguntas de catálogo (conteos, listados) se responden con consultas a SQLite, sin generación text

Además, el historial que se inyecta en el prompt está recortado, la temperatura es baja y la intención se clasifica con el propio modelo local (sin servicios externos).

11. Seguridad y autenticación

  • Registro/login: contraseñas con hash (bcrypt por passlib) y JWT firmado con SECRET_KEY (≥32 caracteres, fuera del repositorio). Hay refresh y logout.
  • Endpoints de negocio: exigen token Bearer; sin token → 401 (verificado en el smoke test). Cada consulta de historial o de documentos verifica la pertenencia al usuario → un token de otro usuario no ve sus datos (T10/T10b).
  • CORS: lista explícita de orígenes en CORS_ORIGINS; en el stack Docker la petición pasa por nginx (/api) y no se necesita CORS.
  • Secretos: nunca se versionan. .env.example documenta cada variable; .gitignore excluye backend/.env, la base de datos y el vectorstore.
  • Servidor sin privilegios en el contenedor (usuario pony) y HEALTHCHECK configurado.

Decisión de autenticación (DEC-05) y su riesgo (R-03)

El equipo eligió Keycloak (recomendado por el enunciado), que quedó implementado con un proveedor intercambiable: AUTH_PROVIDER=local|keycloak. Hoy opera en modo local con JWT propio porque desplegar Keycloak en free tier con la fecha de entrega inmediata añade un servicio de ~512 MB que los free tiers suelen no cubrir. El enunciado lo permite expresamente: «pueden emplear otra solución o implementarla por su cuenta». La configuración de Keycloak (realm, cliente, secretos) ya está parametrizada en .env.example para activarse con una variable, y el plan alternativo está documentado en docs/decisiones.md §4.

Tensión documentada (R-04): el enunciado dice que «ningún endpoint puede quedar expuesto al consumo sin autenticación», pero rutas técnicas como GET /health, el preflight OPTIONS de CORS y las propias rutas de registro/login no pueden exigir token previo (dos de ellas lo obtienen y las demás no tratan datos de negocio). Se documenta abiertamente aquí y se agrupa en docs/matriz-requisitos.md §7: sin token, los endpoints de negocio responden 401 verificado.

Conclusiones

  1. El requisito central — respuestas fundamentadas y rechazo honesto — se cumple con 7 estrategias verificables y 12 pruebas automatizadas, incluido el caso de conocimiento de contexto exigido por el profesor.
  2. LangGraph aportó estructura real al flujo: las rutas condicionales (catálogo, suficiencia, validación) están expresadas como aristas del grafo y son auditables en código, sin constructores visuales.
  3. Un modelo local de 4B es suficiente cuando el RAG hace el trabajo pesado: la calidad de la respuesta depende más de la recuperación y del prompt que del tamaño del modelo.
  4. El punto más delicado del proyecto es el despliegue en free tier con el modelo local (DEC-06/R-06): el túnel al Ollama del portátil es la solución 0 USD elegida y se muestra en la demostración.
  5. Trabajo futuro: activar Keycloak completo si el free tier lo sostiene (§11), búsqueda híbrida léxica+semántica y evaluación sistemática de la calidad de las respuestas.
